Case study · NYC Open Data · Mar–Aug 2026

Which 311 complaints will fall behind?

An end-to-end model that flags, at the moment a request is filed, the New York City service requests most likely to be resolved slower than comparable requests, so supervisors can triage before a backlog forms.

Study 2 · The useful question

Which requests will run slow compared with others of the same type?

New target: a request is delayed if it takes longer than the 75th-percentile resolution time for its complaint type, with thresholds learned from training months only. The type no longer predicts the outcome, so the model has to find signal in timing, location, agency load and request details.

Methodology

How it was built

01 · Data

Live city API

Pulled from the NYC Open Data Socrata API (1.98M requests, Mar–Aug 2026). A 20% systematic sample by ID keeps it laptop-sized. Quality rules are logged: closures before creation, 0-second auto-closures and midnight timestamps.

02 · Features

No leakage

Only fields known at filing time: agency, type, descriptor, location type, channel, hour, weekday, holiday, coordinates, ZIP target-encoding (train-only), and each agency's open backlog at the moment of filing.

03 · Evaluation

Out of time

Train Mar–Jun, tune on July, test once on August. Metrics suited to ranking under imbalance: PR-AUC, precision and recall at a 10% review budget, lift and Brier score. Accuracy is not used.

Limitations, stated honestly

  • The backlog feature is computed on a 20% sample, so it measures relative load, not true open counts.
  • "Closed" in 311 means an agency closed the ticket, not necessarily that the problem was fixed. Some closures are administrative.
  • July and August ran slower than training months, so thresholds learned in spring drift. A production version would re-fit thresholds on a rolling window.
  • ROC-AUC of 0.68 is modest. The value is in ranking: the top decile is ~2× richer in delays than random.
